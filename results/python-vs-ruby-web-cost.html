Python vs Ruby (YJIT) vs JS — which is cheaper to run for web workloads?

Latest runtimes, DB-backed web app. “Cheaper” = throughput, memory, and tail latency under realistic load. 8 stacks across Ruby, Python, and JavaScript (incl. Bun, Deno, NestJS, Rage). 10 workers, 200 concurrency, multi-round. Updated 2026-06-09. Two evidence streams: a controlled local benchmark and a fact-checked web-research sweep.

TL;DR
  1. Async vs threaded matters more than the language — ~9× on I/O (Bun 42k → Django 4.7k). Every async stack beats every threaded one.
  2. I/O throughput: Bun wins (42.5k, leanest RAM, steadiest tail). Rage (29k) rides with the JS pack, beating both Python arms. NestJS pays ~25% + 1.3 GB for being a full framework.
  3. The ORM you pick can matter more than the language: ActiveRecord & Django ORM are nearly free (4–11%), but SQLAlchemy and Prisma each roughly halve throughput (53% / 59%).
  4. CPU splits by task: Ruby+YJIT wins HTML templates (Erubi) and arithmetic; V8/Bun win json and jwt; crypto ties. Python uses the least RAM per CPU task.
  5. Tail latency exposes the bouncy stacks: Bun & Rails steadiest (p99 ~2× median); Django worst (181 ms, 4.9×).

Verdict: No stack wins every axis. Pick async first, then optimize your bottleneck: Bun for I/O throughput, Ruby+YJIT for compute, Python for per-task RAM — and weigh the ORM, which can cost more than the runtime.

The ORM tax — raw driver vs the framework’s ORM

Real apps don’t hand-write SQL; they use an ORM that turns rows into objects. That object-mapping is often the single biggest per-request cost. So every framework also serves /widgets-orm/:id — the same row, same JSON, through its idiomatic ORM. The raw JS arms have no ORM, so their /widgets-orm is hand-mapping (the ~0% baseline that proves the test is clean). RPS, higher better; tax = throughput lost vs the raw endpoint:

The ORM you pick can matter more than the language. ActiveRecord and Django’s ORM are nearly free (mature, C-backed row hydration). What the matrix shows

  1. Concurrency model dominates I/O. All five async arms (15k–42k) beat both threaded arms (4.7k–10k). Bun is 9× Django. It’s about overlapping DB waits, not the language.
  2. Bun (JavaScriptCore) wins I/O outright — fastest, leanest RAM, steadiest tail. Among V8, Deno edges raw node:http; NestJS (full framework) trails the raw runtimes by ~25% and costs the most RAM.
  3. Rage (async Ruby) is the surprise — 29k rides with the JS pack and beats both Python arms, using a fiber-aware ActiveRecord on the Iodine server. Async Ruby is genuinely competitive at scale.
  4. The ORM tax can dwarf the language gap: ActiveRecord & Django ORM cost 4–11%, but SQLAlchemy and Prisma each ~halve throughput. Pick the ORM as carefully as the framework.
  5. CPU depends on the operation (measured raw, not over HTTP): Ruby+YJIT wins templating + arithmetic, V8/Bun win json + jwt, crypto ties. Python is leanest per CPU task. Use the real library — a naive Ruby template ran 4× slower than Erubi.

Caveats

  • Roda dropped. Its idiomatic Sequel ORM corrupts under Falcon’s fibers (23/50 concurrent queries error), the async db-postgres driver isn’t thread-safe (49/50), and the pg gem segfaults under Puma’s fork on this macOS setup. No fair multi-process config. The broader point: async Ruby has no thread-or-fiber-safe ORM today — Rails 7’s pool is fiber-safe (PR #44219), but the pg driver still blocks, so an async ORM needs an async-native driver (which lacks an ORM) or runs threaded.
  • CPU measured raw, not over HTTP — at high concurrency the HTTP CPU numbers measured queueing, not CPU. CPU is the per-call microbench instead.
  • Deno/Bun used node-postgres / Bun-native SQL; native drivers differ. Single box, loopback, tiny DB — real apps sit longer in the DB, compressing these gaps. macOS, not Linux.

Part 2 — Web research (multi-source, fact-checked)

A 100-agent deep-research sweep with adversarial verification. Meta-finding worth stating: no rigorous public head-to-head Ruby-vs-Python-vs-Node cloud-cost benchmark exists — the hard production numbers are Shopify/YJIT first-party (Ruby side). That gap is why the local matrix earns its keep.

YJIT speedup on real Ruby/Rails web workloads

  • Shopify production (Storefront Renderer, I/O- & DB-bound): measured 14.1% end-to-end, improving to 20%+; ~10% (3.2) → ~15% (3.3) → 20%+. >80M req/min on Black Friday 2025 on prerelease YJIT 3.4.
  • Benchmarks overstate real apps: YJIT 3.4 ~92% faster than the interpreter on x86-64 headline benchmarks; micros 3–7×; railsbench ~65%; but component web benchmarks (activerecord, liquid-render) only ~1.19×.
  • Independent: enabling YJIT typically cuts Rails response times 15–25%; one app +22% Puma RPS.

YJIT memory overhead

  • Benchmark average ~21% more memory (Ruby 3.3); in production with copy-on-write across workers, <8% PSS on Shopify SFR. Matches the elevated Ruby RSS seen locally.

CPython 3.13/3.14: does the new JIT or free-threading help web apps?

  • JIT (copy-and-patch): experimental, off by default through 3.14 (PYTHON_JIT=1); release notes publish no speedup figure. Independent: ~10–30% on CPU hot paths after warmup, ~0 for I/O-bound web servers. Consistent with our un-JIT’d CPython being slowest on the pure-arithmetic loop (10.4 ms vs Ruby+YJIT 4.5 ms) — a production deploy gets no JIT today.
  • Free-threading (no-GIL): ~5–10% single-thread penalty now; little throughput for the process-per-core web model (GIL already releases during I/O). Main web benefit is memory sharing, not speed.
  • Net: for I/O-bound web serving, CPython 3.14 ≈ 3.13 ≈ 3.12.

Framework throughput context (TechEmpower R22/23)

Async micro-stacks (Bun, Starlette/FastAPI) rank far above full-stack frameworks on JSON; Django and Rails cluster together well below them. Consistent with the matrix: the async/sync split outweighs the language.

Bottom line for cost

  1. Choose the concurrency model first. Async/event-loop buys ~9× the throughput on I/O-bound JSON here → far fewer/smaller instances. Dominant lever, language-agnostic.
  2. I/O-bound throughput: Bun is cheapest (42.5k, JavaScriptCore beating every V8 runtime), then the JS pack (Deno/Node/Nest ~32–35k) and Rage (29k, async Ruby), then Python/FastAPI (15k). Every async stack beats every threaded one.
  3. Mind the ORM. ActiveRecord and Django ORM are nearly free (4–11%), but SQLAlchemy and Prisma each ~halve throughput — a bigger hit than most language differences. Prisma also adds ~0.5 GB RAM.
  4. Tail latency, not median, is the SLA risk. Bun & Rails hold p99 near 2× their median; Django blows out to 4.9× (181 ms). A great median can hide a bad tail.
  5. CPU-bound: pick the runtime for the operation. Ruby+YJIT wins HTML templating and arithmetic; json and jwt go to V8/Bun; crypto ties. Or push heavy compute to native libs and it barely matters.
  6. Memory: Python leanest per CPU task; Bun leanest serving I/O (485 MB). NestJS+Prisma is the RAM hog (1.8 GB). Don’t expect CPython 3.13/3.14’s JIT or free-threading to cut I/O web cost — they don’t, yet.

One-sentence answer: the async-vs-threaded choice matters more than the language; among async stacks Bun leads on I/O while async Ruby (Rage) is genuinely competitive, the CPU winner depends on the operation, and the ORM can cost more than the runtime — so “cheapest” depends on whether your bill is bound by I/O throughput, a CPU operation, your ORM, or RAM.
